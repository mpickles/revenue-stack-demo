# Decisions
One line each: chose X over Y because Z, accepting T.

- Consent banner: chose two buttons (Accept all / Reject all) over per-signal toggles because the demo only needs on/off for all four signals, accepting no granular choice.
- Consent mode: chose advanced (the container loads with all four signals denied, and Google tags send requests with no cookies) over basic (no Google tag loads until Accept) because Google can then model conversions from visitors who reject, accepting that a visitor who rejects still causes requests to Google, marked gcs=G100, with no cookies and no click IDs. A company whose legal team wants nothing sent before consent would use basic.
- Consent cookie: chose a 180-day first-party cookie (rw_consent) over a session cookie so a returning visitor is not asked again, accepting a stale choice for up to six months unless they use Cookie settings.
- Click IDs on a new landing: chose to replace the whole stored set (last touch) over keeping the first set because the most recent ad click is the one Google and Meta will match an offline conversion to, accepting that earlier touches are lost. A landing with no click IDs or UTMs leaves the stored set alone.
- Click IDs before consent: chose to hold them in memory only over sessionStorage because web storage is storage too and needs the same consent, accepting that a full page reload before the visitor accepts loses them.
- Hidden fields: chose to fill click IDs, UTMs and the GA client ID on submit over at render because capture runs after hydration and consent can change while the form is open, accepting a native submit listener that must run before React's onSubmit (covered by a unit test). All fields, the GA client ID included, stay empty unless consent is granted.
- /api/lead without HUBSPOT_TOKEN: chose to validate, skip HubSpot, log one line and return 200 {delivered:false} over a 5xx because there is no portal yet and the form, thanks page and generate_lead must still be testable, accepting that the browser shows success for a lead that went nowhere.
- HubSpot upsert: chose to leave empty fields out of the upsert over sending blanks so a repeat lead without a click ID does not wipe the one already stored, accepting that a value can never be cleared from the site.
- Enhanced conversions: chose to push user_data {email} on generate_lead lowercased and trimmed but unhashed, over hashing in the page, because the GA4 and Google Ads tags normalise and SHA-256 the value themselves, accepting a plain email in the data layer for that one event. It is the only personal data the data layer ever holds.
- Leads with no employee count: chose a Needs Review Queue over letting them fall into the Small Business Queue because an unknown size is not a small company and a wrong owner costs more than a short wait, accepting that a person has to work the review queue.
- UTM medium in the Flow: chose to lowercase the value inside the Flow over fixing case only on the site because imports and other forms create leads too, accepting that a misspelled medium (paidsocial) still falls to Organic and Direct. The campaign QA agent is the guard for that.
- Edge case test leads: chose a second file (test_leads_edge_cases.csv) over adding rows to test_leads.csv because the repeat leads must load after the originals and the first run stays "20 created, 5 blocked", accepting two imports.
- Salesforce setup in the repo: chose pulling it as metadata files with the Salesforce CLI over screenshots because a reviewer can read the Flow and the rules as files and a change shows up as a diff, accepting one more tool to install.
