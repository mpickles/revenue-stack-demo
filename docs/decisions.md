# Decisions
One line each: chose X over Y because Z, accepting T.

- Consent banner: chose two buttons (Accept all / Reject all) over per-signal toggles because the demo only needs on/off for all four signals, accepting no granular choice.
- Consent mode: chose advanced (the container loads with all four signals denied, and Google tags send requests with no cookies) over basic (no Google tag loads until Accept) because Google can then model conversions from visitors who reject, accepting that a visitor who rejects still causes requests to Google, marked gcs=G100, with no cookies and no click IDs. A company whose legal team wants nothing sent before consent would use basic.
- Consent cookie: chose a 180-day first-party cookie (rw_consent) over a session cookie so a returning visitor is not asked again, accepting a stale choice for up to six months unless they use Cookie settings.
- Click IDs on a new landing: chose to replace the whole stored set (last touch) over keeping the first set because the most recent ad click is the one Google and Meta will match an offline conversion to, accepting that earlier touches are lost. A landing with no click IDs or UTMs leaves the stored set alone.
- Click IDs before consent: chose to hold them in memory only over sessionStorage because web storage is storage too and needs the same consent, accepting that a full page reload before the visitor accepts loses them.
- Hidden fields: chose to fill click IDs, UTMs and the GA client ID on submit over at render because capture runs after hydration and consent can change while the form is open, accepting a native submit listener that must run before React's onSubmit (covered by a unit test). All fields, the GA client ID included, stay empty unless consent is granted.
- /api/lead without HUBSPOT_TOKEN: chose to validate, skip HubSpot, log one line and return 200 {delivered:false} over a 5xx because there is no portal yet and the form, thanks page and generate_lead must still be testable, accepting that the browser shows success for a lead that went nowhere.
- HubSpot upsert: chose to leave empty fields out of the upsert over sending blanks so a repeat lead without a click ID does not wipe the one already stored, accepting that a value can never be cleared from the site.
- Enhanced conversions: chose to push user_data {email} on generate_lead lowercased and trimmed but unhashed, over hashing in the page, because the GA4 and Google Ads tags normalise and SHA-256 the value themselves, accepting a plain email in the data layer for that one event. It is the only personal data the data layer ever holds.
- Leads with no employee count: chose a Needs Review Queue over letting them fall into the Small Business Queue because an unknown size is not a small company and a wrong owner costs more than a short wait, accepting that a person has to work the review queue.
- UTM medium in the Flow: chose to lowercase the value inside the Flow over fixing case only on the site because imports and other forms create leads too, accepting that a misspelled medium (paidsocial) still falls to Organic and Direct. The campaign QA agent is the guard for that.
- Edge case test leads: chose a second file (test_leads_edge_cases.csv) over adding rows to test_leads.csv because the repeat leads must load after the originals and the first run stays "20 created, 5 blocked", accepting two imports.
- Salesforce setup in the repo: chose pulling it as metadata files with the Salesforce CLI over screenshots because a reviewer can read the Flow and the rules as files and a change shows up as a diff, accepting one more tool to install.
- Proof page write-ups: chose to build each page from the build's own README with a short script over writing the pages by hand because a write-up is then written once and the site cannot drift from the repo, accepting one Python dependency (markdown-it-py, pinned) and a build step to remember. A test fails when a page is out of date.
- Proof page hosting: chose to commit the built pages over building them on Vercel because the host then serves plain files with no build settings to break, accepting built files in git and in every diff.
- Proof page diagrams: chose hand-drawn SVG files over loading Mermaid in the browser because the page then needs no script and no second dependency, accepting that a diagram exists twice, once as Mermaid in a README and once as an SVG, and both must be changed together.
- Portfolio home page: chose to make the proof page my personal portfolio, with an about section and my employer named, over keeping it a page for this one project, because one link should say who I am as well as what I built, accepting one exception to the rule that nothing from my employer is in this repo. Client names, colleague names and work numbers stay out.
- Portfolio motion: chose GSAP 3.13.0 (core, ScrollTrigger, SplitText, Flip), loaded from cdnjs at that exact version, over a hand-written script, because the pinned diagram scene, the line reveals and the sliding filter rows are hard to get right by hand, accepting a script from a third-party host and about four small files to load. Every page reads fine with scripts off, and nothing moves when the visitor has reduced motion turned on.
- Portfolio look: chose a technical direction (IBM Plex Sans, Plex Mono only for data, bordered grading tables, one teal accent, light and dark) over the earlier paper and serif look because cream with a serif and a green or clay accent is now a common machine-made look, accepting a plainer page whose personality comes from the tables and the diagram.
- Portfolio accent colour: chose one of five accents picked at random for each visit (teal, cobalt, red, orange, plum) over a single fixed colour because the layout is plain on purpose and a changing accent makes it memorable, accepting that two people may describe the site by different colours. The choice is held for the visit so every page matches, and teal is used when scripts are off.

- Roadwren's rules now live in one page, docs/roadwren-brief.md, and every build reads from it. Chose fleet size in vehicles over employee count as the one qualifying question because the price is per vehicle and real fleet software vendors ask it, accepting a rewrite of the form, the answer keys and the routing rules. Chose never to block a lead (not for rejected cookies, not for a free email address) over rejecting it at the door, because a blocked web lead is never created and nobody can review it.
- Where a visitor came from: chose two Lead fields filled by the site form (Referring Domain, Landing Page) over reading it later from GA4, because the Flow has to pick Organic Search, AI Search, Referral or Direct at the moment the lead is saved, accepting two more hidden fields on the form and no twins on the Opportunity.
- Referrer matching: chose a short written list (five AI assistant domains, six search engine names matched as a whole part of the domain, AI checked first) over a bigger maintained list, because the rule has to fit in a Flow formula and be read in one look, accepting that a new assistant or search engine lands in Referral until the list is updated.
- Answer keys: chose to work out every expected column with a script (crm/salesforce/make_answer_keys.py) over typing them, because a rule change in the brief then changes the keys in one run and a check fails when they drift, accepting that the script is a second copy of the rules.
- Repeat leads in the answer key: chose to mark D01 and D02 "not confirmed, see Part M" with no expected stage or owner over writing a guessed outcome, because how Salesforce treats a repeat is not confirmed and a guessed key would grade the build against a guess, accepting two rows that grade nothing until the hand test is done.
- Rules that overlap: chose the order no fleet size, then under 20 vehicles, then free email, because a lead that is too small needs no review whatever its email, accepting that a free email lead with no fleet size sits in New with no reason.
- Segment and expected annual value: chose to set both from fleet size at every stage over only on MQL, because they describe the company and a reviewer of a held lead wants to see them, accepting a value on leads that are never sent as a conversion.
- Campaign lookup: chose to find the child campaign by its name alone over by name inside the lead's channel, because a mistyped utm_medium then still lands in its real campaign while Lead Source shows Other, accepting that a campaign name must be unique across channels.
- A utm_medium of organic: chose to leave it as channel Other over mapping it to Organic Search, because the brief names five mediums and Organic Search is defined by the referrer, accepting that a hand-tagged organic link shows up as Other until someone fixes the tag.
- Fleet size values: chose to send the band exactly as the visitor reads it (1-19 up to 1,000+) over a separate machine value, because the brief, the form, the lead API and the CRM dropdown then share one spelling, accepting a comma inside a stored value.
- Consent values on a lead: chose to give ad_user_data_consent and ad_personalization_consent the same value over two separate switches because the banner has one Accept all and one Reject all, accepting that the two can never differ until the banner offers a choice per signal.
- Time of the consent choice: chose a second cookie (rw_consent_at, ISO UTC, same 180 days) over putting the time inside rw_consent because the script in the page head reads rw_consent before the container loads and stays untouched, accepting two cookies for one choice. A choice saved before the time was recorded is kept and the banner stays hidden, so that lead carries the saved values and an empty time.
- Consent on a lead that rejected: chose to always send both consent values and the time, on Accept and on Reject, over sending them only with consent, because they record the choice itself and the ad upload needs a "no" on file to leave someone out, accepting that the consent cookies are written for every visitor who answers the banner.
- Lead API and a missing consent value: chose to count it as false over returning a 400 because false is the safe value and a lead is never blocked, accepting that a broken form would save leads as not consented without an error. A value that is present and not a boolean is still a 400.
- HubSpot consent properties: chose to write all three together, and only when the visitor made a choice, over writing false for a lead with no choice, because a submit from a browser that never answered the banner should not overwrite a recorded choice or leave a new value beside an old time, accepting that such a contact has blank consent, which the ad upload treats as no.
- Referring domain: chose the host name only, in lower case, and nothing for the site's own domain (with or without www) or for a referrer that is not a web page, over the full referrer URL, because the channel rule only needs the domain and a full URL can carry a search query, accepting that the page on the other site is lost. The site records the domain and the CRM decides the channel.
- Referrer and landing page storage: chose the same rw_attrib cookie and the same last-touch rule as the click IDs over a second cookie, so a landing with a click ID, a UTM value or a referring domain replaces the UTM values, the referring domain and the landing page together and a direct landing leaves them alone, accepting that a full reload after moving to another page records that page as the landing page.
- Landing page: chose the path with no query string, cut at 200 characters, over the full URL because the query string is where click IDs travel and those already have their own fields, accepting that two landings on one path with different queries look the same.
- Stored click IDs: chose to keep a click ID until a newer click ID arrives over replacing everything on any new touch, because the upload needs the click ID and a later organic visit says nothing about which ad was clicked, accepting that the click ID and the UTM values on one lead can come from different visits. This narrows the earlier line on click IDs on a new landing: the click IDs are replaced as a group only by a landing that carries one.
- Campaign levels: chose three levels (the year, then the channel, then the marketing effort) with the channel also set as the campaign Type, over two levels with no Type, because the common advice is a time or initiative level on top and a field for the channel so reports do not depend on the hierarchy, accepting one more campaign that holds no members and a Type that repeats the parent's name. The channel stays a level because Roadwren has one offer, the demo request, so no other grouping cuts across it.
