How the database decides

Every request, in this order

  1. 1

    The app connects as a database role that cannot switch the rules off.

  2. 2

    Each request tells the database who is signed in, inside its own transaction.

  3. 3

    Every client table refuses by default, then returns only that person's clients.

  4. 4

    A test fails the build if any client table is missing the rule.

Why it is built the way it is

BecauseA bug in one screen must not leak a client.
SoThe database enforces it, not the screen.

Every table is deny by default, and a test fails if a client table is missing the rule.

BecauseA half-applied settings change is worse than a stale one.
SoA settings sync is all or nothing.

One bad row blocks the whole sync, and the last good version stays live.

BecauseOnly staff should get in.
SoCompany sign-in only.

And only once an admin has added the person.

What I chose, and what I turned down

ChoseTwo stores: Postgres for the app's own records, the warehouse for performance data.

Turned downOne store for everything.

Why, and what it costSmall writes are instant and clients are isolated in the database. The cost: a sync job between the two.

ChoseThe signed-in person is set per transaction.

Turned downFiltering in app code, or setting the person once per session.

Why, and what it costShared connections can leak one person's session into the next. The cost: plain SQL migrations, no ORM.

ChoseThe six roles the agency already has.

Turned downFour generic roles.

Why, and what it costPeople should not have to learn my model of their company. I built the generic four first, then redid them.

ChoseA log the app can add to and never edit or delete.

Turned downA history table per feature.

Why, and what it costOne place to answer who changed what. The app's own database role has edit and delete taken away.

ChoseA free server I run myself.

Turned downA managed database at about $40 a month.

Why, and what it costThe brief was $0. The cost: backups quietly failed for the first two days. A restore drill is how I found out.

What broke, and what I did about it

On the day I changed sign-in, everyone was refused.

The check compared two spellings of the same sign-in address.

FixBoth sides now use the same form of the ID. Patched the same day.
On the first run with real data, screens showed $0.

Every date was being sent to the warehouse as empty.

FixFixed before go-live.

What I learned, and what I would do differently

I changed sign-in for everyone at once, and everyone was locked out.
Next timeSwitch one real account that is not mine first. Then everyone.
One client page ran 173 database transactions and hung for over a minute.
Next timeSet a query budget per page from the first screen, and test against it.
On real data, the app had too many pages and felt overwhelming.
Next timeOne screen per job. Add a page only when someone asks for it twice.
