How the database decides

Every request, in this order

  1. A role with no override

    The app connects as a database role that cannot switch the rules off.

  2. Who is asking

    Set inside each request, in its own transaction.

  3. Deny by default

    A table returns only that person's clients.

  4. A test guards it

    The build fails if any client table is missing the rule.

The team's Claude comes in by the same door

The app hosts its own connector. Claude gets the same access rules as the person asking.

What I chose, and what I turned down

ChoseThe database decides who sees what, with the signed-in person set per transaction.

Turned downHiding clients in the screen, or filtering in app code.

WhyA bug in one screen must not leak a client. Cost: plain SQL, no ORM.

ChoseTwo stores: Postgres for the app's own records, the warehouse for performance data.

Turned downOne store for everything.

WhySmall writes are instant. Cost: a sync job between the two.

ChoseA settings sync that is all or nothing.

Turned downApplying the rows that pass.

WhyA half-applied change is worse than a stale one.

4 more choices

ChoseThe six roles the agency already has.

Turned downFour generic roles.

WhyPeople should not have to learn my model of their company.

ChoseA log the app can add to and never edit or delete.

Turned downA history table per feature.

WhyOne place to answer who changed what.

ChoseA free server I run myself.

Turned downA managed database at about $40 a month.

WhyThe brief was $0. Cost: backups failed quietly for two days.

ChoseEvery screen and every Claude tool reads through one data layer. Each warehouse query has a cost cap, and the cache is keyed to the latest load.

Turned downLetting each page query the warehouse itself.

WhyOne place decides who is asking and what it costs. A new load makes the cache stale on its own.

What went wrong, and what I do now

On the day I changed sign-in, everyone was refused.The check compared two forms of the same ID.
FixBoth sides now use the same form. Patched the same day. Next time I switch one real account first.
On the first run with real data, screens showed $0.Every date was being sent to the warehouse as empty.
FixFixed before go-live.
One client page hung for over a minute.It ran 173 database transactions.
Next timeSet a query budget per page from the first screen, and test against it.
The app felt overwhelming on real data.I had built 119 pages.
FixCut to 46. One screen per job.
Runs started from the team's Claude were refused.The connector signed in as itself, and the runner only accepts the app's identity.
FixThe connector now asks for a token as the app's account, with a narrower permission than first planned after a security review.
