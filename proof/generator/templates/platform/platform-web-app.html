How the database decides

Every request, in this order

  1. 1

    The app connects as a database role that cannot switch the rules off.

  2. 2

    Each request tells the database who is signed in, inside its own transaction.

  3. 3

    Every client table refuses by default, then returns only that person's clients.

  4. 4

    A test fails the build if any client table is missing the rule.

What I chose, and what I turned down

ChoseThe database decides who sees what, with the signed-in person set per transaction.

Turned downHiding clients in the screen, or filtering in app code.

Why, and what it costA bug in one screen must not leak a client, and shared connections can leak a session. The cost: plain SQL migrations, no ORM.

ChoseTwo stores: Postgres for the app's own records, the warehouse for performance data.

Turned downOne store for everything.

Why, and what it costSmall writes are instant and clients are isolated in the database. The cost: a sync job between the two.

ChoseA settings sync that is all or nothing.

Turned downApplying the rows that pass.

Why, and what it costA half-applied change is worse than a stale one. One bad row blocks the sync and the last good version stays live.

3 more choices

ChoseThe six roles the agency already has.

Turned downFour generic roles.

Why, and what it costPeople should not have to learn my model of their company. I built the generic four first, then redid them.

ChoseA log the app can add to and never edit or delete.

Turned downA history table per feature.

Why, and what it costOne place to answer who changed what. The app's own database role has edit and delete taken away.

ChoseA free server I run myself.

Turned downA managed database at about $40 a month.

Why, and what it costThe brief was $0. The cost: backups quietly failed for the first two days. A restore drill is how I found out.
